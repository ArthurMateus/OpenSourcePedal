## Why processor profiles are necessary
The first validation run (head 270076d, run 40726002769) failed 14 R checks using the original single profile.
It ran on AMD Family 25 Model 1; calibration used Family 26 Model 2. Benchmark C++ was byte-for-byte unchanged
between those heads (git diff 6a3b3e4..270076d -- tests/bench/bench_common.h tests/bench/osp_bench.cpp
 tests/bench/entries is empty), and both image versions were 20261026.347.1. Observed five-run median changes:
input_stage +48.62%, doubler +20.62%, FIR oversampling +27.68%, while spring_tank changed -0.15%.
A single reference kernel does not normalise this cross-processor workload difference. A broad allowance
would lose the required +20% detection, so each case stores separately measured processorBaselines instead.
The canonical top-level r0/baseline remains Family 26 Model 2 for legacy offline commands. CI passes
--runner build/bench-runner.json; an unknown processor or missing per-case profile fails with a calibration
instruction. New entry files keep the same C++ API and add profiles in their own budget fragment only.
CPU-only --no-regression mode needs no profile. Runners are not retried to obtain a preferred processor family;
all five samples are retained without filtering.

Within Family 26 Model 2 the raw EQ spread was 37.76% from one high sample (0.218377872); median 0.165060434.
Spring raw spread was 13.61%. All five samples remain included. Family 25 Model 1's largest raw spread was 7.83%.
Final CI must independently pass the selected profile's strict 10% check. See PR/issue comments for that later
validation and merge verdict; this note is the pre-merge checkpoint.
